# Vanta — Supabase Infrastructure Setup

This directory contains the SQL migration files for the Vanta platform's
Supabase infrastructure. These files define the **target schema** that the
application will migrate to in subsequent phases.

The existing SQLite-backed server continues to operate unchanged until
the application code is migrated in later phases.

---

## File Order

Execute the files in this exact order in the Supabase SQL Editor:

| Order | File | Purpose |
|-------|------|---------|
| 1 | `001_schema.sql` | Tables, indexes, constraints, profile trigger |
| 2 | `002_rls.sql` | Row Level Security policies + Storage policies |
| 3 | `003_functions.sql` | pgvector RPC functions |

---

## Step 1 — Create a Supabase Project

1. Go to [supabase.com](https://supabase.com) and sign in.
2. Click **New project**.
3. Choose your organisation, set a project name (e.g. `vanta`), choose a
   region close to your users, and set a strong database password.
4. Wait for the project to finish provisioning (~2 minutes).

---

## Step 2 — Enable pgvector

pgvector is enabled automatically by `001_schema.sql` via:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

You do not need to enable it manually. It will be activated when you run
`001_schema.sql` in Step 4.

To verify it was enabled after running the SQL:

```sql
SELECT * FROM pg_extension WHERE extname = 'vector';
```

Expected: one row returned.

---

## Step 3 — Run the SQL Files

1. In the Supabase dashboard, go to **SQL Editor** → **New query**.
2. Paste the full contents of `001_schema.sql` and click **Run**.
3. Open a new query tab. Paste `002_rls.sql` and click **Run**.
4. Open a new query tab. Paste `003_functions.sql` and click **Run**.

Each file must complete without errors before running the next.

If you need to re-run a file (e.g. after a schema change), the statements
use `CREATE TABLE IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`, and
`DROP TRIGGER IF EXISTS` so they are safe to re-execute.

---

## Step 4 — Create the Storage Bucket

The `knowledge-docs` bucket **must be private**. Do not enable public access.

1. In the Supabase dashboard, go to **Storage** → **New bucket**.
2. Set the bucket name exactly: `knowledge-docs`
3. Leave **Public bucket** toggled **OFF**.
4. Click **Create bucket**.

The storage RLS policies in `002_rls.sql` apply automatically to this bucket
once it exists. The Express server uses the service role key for all storage
operations (upload, signed URL generation, deletion) and bypasses these
policies — they are a defence-in-depth layer only.

### Storage path convention

All uploaded files are stored at:

```
{user_id}/{rag_app_id}/{document_id}/{safe_filename}
```

- `user_id` — Supabase Auth UUID of the uploading user
- `rag_app_id` — UUID of the RAG application
- `document_id` — UUID generated by the Express handler before upload
- `safe_filename` — sanitized version of the original filename
  (alphanumeric, hyphens, underscores, dot-extension only)

The unsanitized original filename must **never** appear directly in the
storage path to prevent path traversal issues.

## Step 5 — Collect Environment Values

### Server environment (`server/.env`)

| Variable | Where to find it | Exposure |
|----------|-----------------|---------|
| `SUPABASE_URL` | Supabase dashboard → Settings → API → **Project URL** | Server only |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase dashboard → Settings → API → **service_role** key (under "Project API keys") | **Server only — never expose to browser** |

The service role key bypasses all RLS policies. It must only ever be present
in server-side environment variables. Never commit it to git or pass it to
the client.

### Client environment (`client/.env`)

| Variable | Where to find it | Exposure |
|----------|-----------------|---------|
| `VITE_SUPABASE_URL` | Same as `SUPABASE_URL` above | Browser-safe |
| `VITE_SUPABASE_ANON_KEY` | Supabase dashboard → Settings → API → **anon** key (under "Project API keys") | Browser-safe |

The `anon` key is designed to be public. RLS policies determine what
authenticated and anonymous users can access with this key.

### Local embedding model (`server/.env`)

```
TRANSFORMERS_CACHE=./data/models
```

This controls where `@huggingface/transformers` caches the
`BAAI/bge-small-en-v1.5` model weights after the first download.
The model is approximately 130 MB. It is downloaded once on first server
startup after Phase 2 of the migration.

**Do not install or initialise the embedding model during Phase 0.**

### Complete future `server/.env` example

```
# LLM (already present)
OPENAI_API_KEY=sk-or-v1-...

# Supabase (add in Phase 1)
SUPABASE_URL=https://<project-ref>.supabase.co
SUPABASE_SERVICE_ROLE_KEY=eyJ...

# Local embedding model cache (add in Phase 2)
TRANSFORMERS_CACHE=./data/models

# Server
PORT=3001
```

### Complete future `client/.env` example

```
# Supabase (add in Phase 6)
VITE_SUPABASE_URL=https://<project-ref>.supabase.co
VITE_SUPABASE_ANON_KEY=eyJ...

# API proxy target (empty = use Vite proxy in dev)
VITE_API_URL=
```

## Step 7 — Verify RLS

### Verify anonymous users cannot read rag_apps

In the SQL Editor, run:

```sql
-- Simulate an anonymous (unauthenticated) request
SET LOCAL role = anon;
SELECT * FROM rag_apps;
```

Expected: `0 rows` (RLS blocks anonymous access).

Reset after testing:

```sql
RESET role;
```

### Verify authenticated user sees only their own rows

1. Create two test users (User A and User B) via Authentication → Users.
2. Manually insert a project and rag_app for User A using the service role
   (paste directly in SQL Editor):

```sql
-- Insert a project for User A
INSERT INTO projects (id, user_id, name)
VALUES (
  gen_random_uuid(),
  '<user_a_uuid>',
  'Test Project'
);

-- Insert a rag_app for User A
INSERT INTO rag_apps (id, user_id, project_id, title)
VALUES (
  gen_random_uuid(),
  '<user_a_uuid>',
  (SELECT id FROM projects WHERE user_id = '<user_a_uuid>' LIMIT 1),
  'Test App'
);
```

3. Sign in as User B in a browser and make a direct Supabase client call
   (or use the API explorer in the dashboard with User B's JWT):

```sql
SELECT * FROM rag_apps WHERE user_id = '<user_a_uuid>';
```

Expected: `0 rows` (RLS hides User A's row from User B).

### Verify service role bypasses RLS

Run from SQL Editor (which uses service role):

```sql
SELECT * FROM rag_apps;
```

Expected: all rows visible, including the one inserted for User A.

## Step 8 — Verify pgvector

Verify the extension is active:

```sql
SELECT extname, extversion FROM pg_extension WHERE extname = 'vector';
```

Verify a 384-dim vector is accepted:

```sql
-- Insert a test chunk with a 384-dimensional zero vector
INSERT INTO document_chunks (
  user_id, rag_app_id, document_id, node_id,
  file_name, content, embedding, chunk_index
)
SELECT
  p.id,
  ra.id,
  d.id,
  'test-node',
  'test.txt',
  'This is a test chunk.',
  array_fill(0, ARRAY[384])::vector(384),
  0
FROM profiles p
JOIN rag_apps ra ON ra.user_id = p.id
JOIN documents d ON d.rag_app_id = ra.id
LIMIT 1;
```

Note: this INSERT requires that at least one profile, rag_app, and document
already exist. If test data is not available, use a simpler dimension check:

```sql
-- Verify 384-dim vector is accepted
SELECT '[' || array_to_string(array_fill(0, ARRAY[384]), ',') || ']'::vector(384);
```

Expected: returns a vector value without error.

Verify wrong dimension is rejected:

```sql
-- Verify 1536-dim vector is rejected by vector(384) column
SELECT '[' || array_to_string(array_fill(0, ARRAY[1536]), ',') || ']'::vector(384);
```

Expected: error — `expected 384 dimensions, not 1536`.

## Step 9 — Verify match_chunks RPC

Requires at least one `document_chunks` row with a real 384-dim embedding.
If none exist yet, this function can still be verified for correct signature:

```sql
-- Verify the function exists and accepts the correct types
SELECT proname, pronargs
FROM pg_proc
WHERE proname = 'match_chunks';
```

Expected: one row, `pronargs = 3`.

Once test data exists:

```sql
SELECT * FROM match_chunks(
  array_fill(0, ARRAY[384])::vector(384),
  '<rag_app_id_uuid>',
  5
);
```

Expected: returns rows with `id`, `content`, `file_name`, `score` columns.
With a zero query vector, scores will be 0 or NaN — this is expected for
a zero-vector test. The important thing is the function executes without error.

## Architecture Notes

### Why vector(384) not vector(1536)

The embedding model `BAAI/bge-small-en-v1.5` via `@huggingface/transformers`
produces 384-dimensional vectors. OpenAI `text-embedding-3-small` (1536-dim)
is not used — OpenRouter is the LLM provider and does not expose an embeddings
endpoint. All embeddings are generated locally.

### Why no pseudo-embedding fallback

The `embedding vector(384) NOT NULL` constraint enforces that chunk inserts
must carry a real embedding. If embedding generation fails, the Express
handler sets `documents.status = 'error'` and returns HTTP 422 without
inserting any chunk rows. This prevents silently degraded retrieval quality.

### Why no anonymous RLS policies

Public embed access (chatbot widget) goes through the Express API using
`embed_id`. The Express backend uses the service role key and returns only
the minimal fields needed. This avoids exposing every deployed app's data
to anonymous queries and allows the Express layer to enforce additional
business logic (rate limiting, analytics, etc.) in future.

### Future HNSW index

When exact search latency exceeds acceptable thresholds (typically >10k chunks
per RAG app), run the migration documented in `001_schema.sql`:

```sql
CREATE INDEX idx_chunks_embedding
  ON document_chunks
  USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
```

HNSW is preferred over IVFFlat: no training step, incremental insert support,
better recall/latency tradeoff for this workload.
